# ParallelMe v0.7 · Upgrade Plan

> 当前升级方向：从流程化五声会谈，转向由书记员牵引的五声圆桌。v0.7 的目标不是增加更多角色、更多阶段或更多生成内容，而是压缩用户动线，让用户用更少动作把议题定义清楚，再在固定五声的圆桌中看见自己的价值倾向。

## 1. Upgrade Thesis

v0.7 要解决的核心问题：

- 当前会谈动线太长：陈情、追问、工作焦点、五声入席、表态、点名追问、换位、互问、NowMe、承诺、记忆确认被拆成太多关卡。
- 用户每一步都要决定“下一步点什么”，但很多节点的目标并不清楚。
- 五声输出偏散文式，用户需要读很多内容才能比较不同声音的立场。
- “声浪最大”等粗指标不再适合作为判断依据，用户真实偏好应该从圆桌中的提问、续轮、对峙、补充和书记员问询里浮现。

v0.7 的总体动线：

```text
原始输入
→ 书记员整理本次议题
→ 用户完成一次主交互
→ 用户确认本次议题
→ 五声圆桌
→ 书记员追踪偏好并提出关键问题
→ 清明句落定
```

## 2. Design Principles

- 固定五声，不再有入席、临时席位、新声音或角色扩展。
- 书记员半显性存在，但不是第六声；它没有价值立场，只负责整理、记录、比较和落定。
- 用户不是在填问卷，而是在低成本校准书记员对本次议题的理解。
- AI 起草，用户裁决：书记员先把混乱整理成可审阅草稿，用户只需要判断准不准。
- 写一次，用多次：用户只必须写一次原始输入，后续尽量通过选择、提问、补一句和原地改写推进。
- 改写永远在原地：不弹窗、不跳页，哪一格不准就在哪一格改。
- 五声不是自由聊天头像，而是五种稳定价值立场。
- 圆桌不是辩论赛，不追求谁赢；它帮助用户看见自己更靠近什么、更抗拒什么、愿意承认什么代价。
- 清明句不再由 NowMe 作为单独角色输出，而由书记员基于议题、圆桌内容和用户偏好轨迹整理。

### 2.1 Product Pattern Translation

同类自我记录产品给 v0.7 的启发：

- 低输入摩擦优先。像 Daylio 这类 mood journal 的核心优势是用选择和标签完成记录，写作只是补充。
- 情绪或状态需要被“命名”。How We Feel 的情绪词与矩阵给出的启发是：用户常常不是没有感受，而是缺少可选的精确语言。
- 记录的价值来自回看与模式识别，而不是当场生成一大段解释。
- 对话式产品容易显得“很会说但不真正记得”。v0.7 要避免只做聊天，要让书记员把用户动作沉淀成可追踪的结构。

翻译到 ParallelMe：

- 第一阶段用选择卡降低表达成本。
- 圆桌阶段用固定五声提供稳定语言框架。
- 书记员负责把选择、提问、对峙和改写记录成结构化痕迹。
- 清明落定给用户带走的是一句判断、一段偏好读数、一个代价承认和一个 24h 承诺。

## 3. Retired Concepts

v0.7 明确删除或降级这些概念：

- `activatedVoices`
- `activatedReason`
- `source: "standing"`
- 五声入席
- 临时席位
- 新增声音
- 新角色
- 声音升格
- 声浪最大 / 声浪最小
- `loudestVoiceId`
- `loudestVoiceName`
- 由文本长度或语气强度推断某声“最响”
- 点名追问、换位回答、五声互问这些作为固定流程关卡的设计

这些能力中有些可以以新形式回到圆桌里，例如“让某一声继续说”“让两声对峙”，但它们不再是固定阶段。

## 4. The Scribe

书记员是 v0.7 的结构化认知层。

它负责：

- 把用户原始输入整理成本次议题。
- 生成少量高密度选择卡。
- 将用户选择转成结构化 KV。
- 让五声的发言保持可比较。
- 记录用户在圆桌中的提问、续轮、对峙、补充和改写。
- 在圆桌后提出关键问题，验证它对用户偏好的推测。
- 整理清明句、偏好读数、代价承认、此刻落点和 24h 承诺。

它不负责：

- 作为第六个声音发言。
- 劝用户做重大决定。
- 诊断用户。
- 给心理治疗式解释。
- 宣布哪个声音最大、最小、最好或最正确。

产品上，书记员可以半显性出现：

- “书记员正在整理本次议题”
- “书记员记录到：你更靠近这句话”
- “书记员想确认一个关键分歧”

但它不应该有头像、人格、情绪或价值立场。

## 5. Stage One: 本次议题

第一阶段只做一件事：

> 把用户的一团原始输入定义成一个清楚、可讨论的议题。

用户先给出原始输入。书记员随后生成少量高密度选择卡。用户完成一次主交互后，系统展示整理好的“本次议题”，用户确认后直接进入圆桌。

这一阶段不再是：

- 多轮追问。
- 开放题表单。
- 逐个 KV 让用户确认。
- 追问后再生成工作焦点。
- 引入五声。

### 5.1 User Interaction

第一阶段只有一次主交互。这里的“一次主交互”指一个连续的议题定义环节，而不是严格只出现一组题。

形式是少量高密度选择卡，用户在同一个卡位内逐题完成：

- 点选后自动进入下一题。
- 可以返回上一题。
- 每题最后保留“都不准，我补一句”。
- 完成后直接展示“本次议题”。
- 不出现追问式循环，不因为某个内部字段低确定就不断追加题目。只有当书记员无法生成可确认的“本次议题”时，才允许追加一组高密度选择卡。

选择卡的目标不是收集答案数量，而是用一个选择更新一组结构化 KV。

题数和选项数不做硬编码。书记员的目标是：用最小步数提出高密度、高质量、有价值的问题，把本次议题定义清楚。工程上可以给模型少量高质量分支样例，但不要把样例当固定题库。

例如，用户选择：

> 我不是不想稳定，我是讨厌被催着决定。

书记员内部可以记录：

```ts
decision_pressure = "high"
autonomy_sensitivity = "high"
stability_desire = "present_but_conflicted"
family_pressure_meaning = "pressure_more_than_support"
```

选择卡不是固定题库。它应该由书记员根据原始输入生成，但可以通过少量高质量示例教会模型什么是“高密度选择”：

- 一个选项要能同时更新多个 KV。
- 选项之间要代表不同的解释路径，而不是同一句话的轻微改写。
- 至少保留一个“不完全贴合”的出口，让用户补一句。
- 不使用心理学术语作为选项文本。

“我自己说”只补充当前题，不直接改写整张本次议题。完成这一组题后，书记员统一消化所有选择和补充，再生成“本次议题”。

返回上一题只发生在同一组题内。若书记员完成一组题后仍无法生成可确认的“本次议题”，新问题属于新的判断回合，用户不再回到上一组逐题修改；上一组已经进入书记员消化结果。

当原始输入过短或过抽象时，可以触发一次兜底扩写，但最多一次。

例：

```text
你写的“我好累”我听到了。再陪我说一点：

○ 是某件具体的事让你累
○ 是某段关系让你累
○ 是看不到尽头让你累
○ 我自己说
```

扩写后，书记员重新整理本次议题；不进入无限追问。

### 5.2 Visible Task Frame

用户可见层应该是自然语言，不展示 JSON。

```ts
type VisibleTaskFrame = {
  problem_definition: string
  current_state: string
  key_facts: string[]
  main_choices: string[]
  core_conflict: string
  central_question: string
  main_concerns: string[]
  discussion_focus: string
}
```

这些字段都应该展示。若后续发现某两个字段长期重复，就合并字段，而不是折叠隐藏。第一阶段的问题设计本身就要围绕这些字段生成；用户确认后，这些字段全部进入五声圆桌。

每个可见字段可以带一个轻量来源标签，帮助用户分辨哪些是系统读出的，哪些是系统推测的，哪些来自自己的选择：

```ts
type VisibleSourceLabel = "读出" | "我猜的" | "你说的"
```

对应内部证据状态：

- `读出`：来自用户原始输入中的明确内容。
- `我猜的`：书记员为组织议题做出的推断，用户最应该能轻易改掉。
- `你说的`：来自用户选择、补充或确认。

这些标签应该小而克制，像纸页边注，不要做成测评徽章。

#### `problem_definition`

一句话定义这次真正的问题。

例：

> 你现在卡住的不是单纯要不要考公，而是妈妈期待的稳定路径，和你当前收入、自主生活之间的冲突。

#### `current_state`

用户此刻与这个问题的关系，不做诊断。

例：

> 你现在还没有准备立刻做决定，更像是在确认自己到底抗拒什么、在乎什么。

#### `key_facts`

已知事实。优先来自用户原始输入和用户选择。

例：

- 妈妈希望你考公。
- 你现在在大厂，月薪约 2.5w。
- 回老家后月薪可能约 6k。

#### `main_choices`

当前浮现的几条路。

例：

- 继续留在当前路径。
- 认真考虑考公或回老家。
- 暂时不做最终决定，先弄清楚自己要什么。

#### `core_conflict`

核心冲突，短而清楚。

例：

> 稳定与家庭安心 vs 收入、自主和当前生活路径。

#### `central_question`

这件事真正问用户的是什么。

用户界面上不显示字段名，显示为：

> 这件事问你的是 ——

例：

> 我能不能不靠让妈妈安心来证明自己选得对。

这个字段是第一阶段最有穿透力的一格。它不是事实，也不是建议，而是把表层选择往下压一层，形成一个用户可以承认或反驳的内在命题。

生成约束：

- 尽量使用“我能不能……”或“我是不是……”句式。
- 不复述表层选项。
- 不诊断，不医学化，不使用专业术语。
- 可以锋利，但不能替用户定罪。

#### `main_concerns`

本次议题牵动的主要点。

例：

- 收入差距。
- 妈妈的期待与担心。
- 自己是否会后悔。
- 生活半径变化。
- 被催着决定的不舒服。

#### `discussion_focus`

进入圆桌前的任务句。

例：

> 这场圆桌先讨论：你是否愿意为了稳定和妈妈安心，牺牲一部分收入与自主感。

### 5.2.1 Review And Inline Edit

“本次议题”展示后，用户可以确认，也可以原地修改任意一格。

原则：

- 不弹窗。
- 不跳页。
- 不重启选择卡。
- 修改后该字段标记为 `user_confirmed` 或 `user_edited`。
- 用户手改内容在本次圆桌中优先级高于模型推断。

主动作保持简单：

```text
确认，进入五声圆桌
这不准，我改一句
```

“这不准”不是错误状态，而是书记员校准的一部分。

### 5.3 Internal Task Frame

内部可用层服务书记员和后续圆桌，不直接展示给用户。

```ts
type InternalTaskFrame = {
  facts: FactKV[]
  parties: PartyKV[]
  options: OptionKV[]
  state_tags: StateTags
  value_axes: ValueAxis[]
  pressure_sources: PressureSource[]
  concern_notes: ConcernNote[]
  source_labels: SourceLabelMap
  choice_answers: ChoiceAnswer[]
  evidence: EvidenceState
}
```

#### `facts`

结构化事实。用户确认后，事实不再需要模型置信分，而是记录证据来源。

```ts
{
  key: "current_income",
  value: "25000/month",
  evidence_status: "user_confirmed",
  source: "raw_input"
}
```

#### `parties`

相关方和关系位置。

```ts
{ key: "mother", role: "pressure_source" }
```

#### `options`

当前可能路径。

```ts
{
  key: "stay_current_job",
  label: "继续当前路径",
  evidence_status: "model_inferred"
}
```

#### `state_tags`

用户当前状态标签，只作内部编排参考。

```ts
{
  clarity: "low",
  decision_readiness: "exploring",
  urgency: "medium",
  emotional_charge: "medium"
}
```

#### `value_axes`

本次议题里的价值冲突轴。

```ts
{
  key: "stability_vs_autonomy",
  side_a: "稳定和家庭安心",
  side_b: "自主与当前生活路径",
  evidence_status: "user_selected"
}
```

#### `pressure_sources`

压力来源。

```ts
{
  key: "family_expectation",
  from: "mother",
  kind: "expectation",
  evidence_status: "user_selected"
}
```

#### `concern_notes`

主要牵动点。只记录内容和证据，不给分、不排序。

```ts
[
  {
    key: "money",
    text: "收入差距牵动现实退路",
    evidence_status: "raw_explicit"
  },
  {
    key: "family_relationship",
    text: "妈妈的期待正在形成压力",
    evidence_status: "user_selected"
  }
]
```

#### `source_labels`

可见字段的来源标签映射。

```ts
{
  problem_definition: "读出",
  current_state: "我猜的",
  central_question: "你说的"
}
```

来源标签不是置信分，而是产品层面的诚实：

- 哪些是书记员从原文读出来的。
- 哪些只是书记员的推测。
- 哪些已经经过用户选择或修改。

#### `choice_answers`

用户选择卡的回答痕迹。

```ts
{
  card_id: "main_stuck_point",
  selected_option_id: "hate_being_pushed",
  derived_kv: {
    decision_pressure: "high",
    autonomy_sensitivity: "high"
  }
}
```

#### `evidence`

记录字段证据状态，不把模型推断伪装成用户事实。

```ts
type EvidenceStatus =
  | "raw_explicit"
  | "user_selected"
  | "user_confirmed"
  | "user_edited"
  | "model_inferred"
  | "not_clear"
```

### 5.4 Evidence Without Scoring

v0.7 不把用户状态、价值冲突或压力来源包装成科学量表。

更准确的设计是：

- 对事实使用证据状态，而不是置信分。
- 对价值冲突、压力来源、牵动点只记录证据状态和自然语言说明。
- 对低确定字段保留 `model_inferred` 或 `not_clear`，避免后续模型把它说死。

用户确认后，并不意味着所有内部推断都 100% 成立。用户确认的是可见的“本次议题”；内部字段仍需要区分：

- 用户原文明确说过。
- 用户在选择卡里选过。
- 用户确认过可见表述。
- 用户亲手改过某一格。
- 模型为了组织圆桌做出的推断。

因此，事实可以在用户确认后变成 `user_confirmed`。价值轴、压力来源和牵动点不需要显著性等级。书记员可以在运行时判断先讨论什么，但这类判断不作为用户画像或声音分布记录。

这些内部记录只用于：

- 决定圆桌优先讨论什么。
- 帮五声避免泛泛发言。
- 帮书记员提出更有针对性的问题。
- 帮清明句引用用户实际确认过的重点。

### 5.5 Stage One Acceptance

第一阶段成功时，不是所有内部字段都被“测准”，而是用户愿意承认：

> 对，这次先讨论的是这个。

具体表现：

- 用户没有被迫继续写长文本。
- 用户能看见书记员从原文读出了什么。
- 用户能轻易改掉“我猜的”内容。
- “这件事问你的是 ——”能让用户产生一次轻微停顿。
- 确认后，圆桌有足够清楚的共同议题。

## 6. Stage Two: 五声圆桌

五声永远固定存在：

- 躺平的我
- 搞钱的我
- 出走的我
- 被牵挂的我
- 5 年后的我

不再需要“入席”。进入圆桌时，五声直接围绕“本次议题”发表第一轮看法。

### 6.1 Research Translation

圆桌会的心理学依据不直接暴露给用户，但要约束产品设计。

参考：

- [IFS Institute · Internal Family Systems Model Outline](https://ifs-institute.com/resources/articles/internal-family-systems-model-outline)
- [Voice Dialogue International](https://halstone.com/)
- [Chairwork systematic review · PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC12876151/)
- [Motivational Interviewing · NCBI Bookshelf](https://www.ncbi.nlm.nih.gov/books/n/tip35v2/ch3/)
- [ACT · Association for Contextual Behavioral Science](https://contextualscience.org/act)

翻译成产品规则：

- 每个声音都有正向保护意图。没有“坏声音”，也不把某个声音设计成反派。
- 用户不能被某一个声音吞没。产品要帮助用户从“我就是这个声音”退到“我正在听见这个声音”。
- 相反立场之间的张力是有价值的。圆桌应该允许对峙，但对峙的目标是看见代价和盲点，不是攻击。
- 空间布局有意义。五声的可见位置、轮次和对话痕迹应该帮助用户外化内在冲突。
- 书记员要采用反映、总结和自主支持的语气，不审判、不逼迫改变。
- 最后看重的是价值澄清和可行姿态，而不是情绪被消灭或所有声音达成一致。

### 6.2 Roundtable Layout

圆桌界面建议采用上半圆扇形，但视觉上仍然保持纸墨秩序：

- 五个角色沿上半圆展开。
- 每个角色下方沉淀自己的发言轮次。
- 中间或底部保留书记员台。
- 用户可以整体推动下一轮，也可以点某一个声音继续说。
- 移动端可以退化为横向五声轨 + 当前声音详情，不强行挤出完整半圆。

布局目标：

- 用户一眼看见五个声音都在场。
- 用户能横向比较同一轮里五个声音的不同立场。
- 用户能纵向查看某一个声音如何变化。
- 用户能清楚区分“声音发言”和“书记员记录”。

### 6.3 Voice Persona Refinement

v0.7 的五声人格要从“靠口头禅维持角色感”，升级为“靠价值函数和注意力方向稳定角色”。

每个声音应稳定具备：

- 它守护的价值。
- 它最容易注意到的问题角度。
- 它最常误判或过度掌权的风险。
- 它在圆桌里最适合提出的提醒。

#### 躺平的我

- 守护：低消耗、身体、睡眠、神经系统。
- 注意：用户是否已经被消耗到无法判断。
- 提醒：先让人恢复，选择才有质量。
- 风险：把恢复变成逃避，把暂停变成长期停摆。

#### 搞钱的我

- 守护：现金流、退路、现实边界、选择权。
- 注意：成本、机会、风险、长期资源。
- 提醒：没有现实底盘的自由很容易变成新焦虑。
- 风险：把一切价值都折算成收益。

#### 出走的我

- 守护：自由、生命力、出口、重新开始。
- 注意：用户是否正在被旧环境压到失去呼吸感。
- 提醒：不是所有痛苦都该靠忍耐解决。
- 风险：把所有痛苦都理解成“离开就好”。

#### 被牵挂的我

- 守护：关系、归属、责任、重要他人的安心。
- 注意：用户的选择会牵动谁，以及用户是否把亏欠当责任。
- 提醒：不必假装家人和亲密关系不重要。
- 风险：替所有人的情绪负责，忘记自己也是相关方。

#### 5 年后的我

- 守护：时间尺度、长期连续性、未来可回看的自己。
- 注意：当前情绪是否正在把短痛伪装成命运。
- 提醒：把今天放进更长时间里看。
- 风险：过度抽离当下痛苦，显得像不近人情。

### 6.4 Opening Argument Structure

五声第一轮是立论。它为整个圆桌定基调，因此要结构化、可比较、短而有力。

```ts
type VoiceOpeningTurn = {
  voice_id: VoiceId
  round_id: string
  thesis: string
  protected_value: string
  concern: string
  task_evidence: string
  pull: string
  overreach_cost: string
}
```

用户界面上使用中文标签：

```text
我先站在
我在保护
我担心
我抓住的依据
我会拉你去
只听我的代价
```

字段含义：

- `thesis`：这个声音的一句话立论，要带一点声音质地。
- `protected_value`：它这次最想保护的价值。
- `concern`：它最担心用户忽略什么。
- `task_evidence`：它从本次议题里抓住了哪条事实或命题。
- `pull`：它会把用户往哪个方向拉。
- `overreach_cost`：如果过度听从它，会牺牲什么。

第一轮之后，不要求每次发言都完整输出六项。后续发言根据动作类型生成更自然的一来一回。

```ts
type VoiceRoundTurn =
  | VoiceOpeningTurn
  | VoiceContinuationTurn
  | VoiceResponseTurn
  | DuelExchange

type VoiceContinuationTurn = {
  voice_id: VoiceId
  trigger: "continue_all" | "continue_one"
  text: string
  refers_to?: VoiceId[]
}

type VoiceResponseTurn = {
  voice_id: VoiceId
  trigger: "user_to_voice" | "user_to_table"
  text: string
  acknowledged_user_input?: string
}

type VoiceTurnTrigger =
  | "opening"
  | "continue_all"
  | "continue_one"
  | "duel"
  | "user_to_voice"
  | "user_to_table"
```

第一轮每个字段都要短，避免五张卡片变成五篇文章。建议：

- `thesis` ≤ 36 字。
- `protected_value` ≤ 24 字。
- `concern` ≤ 32 字。
- `task_evidence` ≤ 36 字。
- `pull` ≤ 32 字。
- `overreach_cost` ≤ 36 字。

五声人格暂时不随会谈更新。v0.7 先通过固定模板和 prompt 约束稳定这五个声音，而不是根据用户反馈改写角色人格。

### 6.5 Phase A: 自由圆桌

圆桌第一段是自由会谈。用户像主持人一样推动讨论：

```text
五声第一轮发言
→ 用户自由推动讨论
→ 书记员在旁记录动作和偏好痕迹
```

第一轮在进入圆桌后自动发生。五声都围绕“本次议题”发表结构化看法。

随后用户可以：

- 让五声依次再说一轮。
- 让某一个声音基于所有人发言继续说。
- 选择两个声音，让 A 向 B 对峙。
- 向某一个声音发问。
- 向全体圆桌发言。
- 请求书记员整理一下。

这些动作都由书记员记录为数据语言。

### 6.6 User Action Language

用户动作要低成本、语义清楚，并能被书记员记录成数据语言。自由圆桌不使用死板反应标签，例如“接近我 / 不准 / 刺中我 / 我想再听”。这些偏好由书记员在后续问询中主动验证。

操作台平铺主要动作，不依赖点击某个声音后再展开多层菜单。

建议动作：

```text
再来一轮
让某声继续
问某一声
问全桌
两声对峙
书记员整理
结束自由圆桌
```

```ts
type UserRoundtableMove =
  | ContinueAllMove
  | ContinueOneMove
  | DuelMove
  | AskVoiceMove
  | AskTableMove
  | AskScribeMove
  | EndFreeRoundtableMove

type MoveSignal =
  | "continue_all"
  | "continue_one"
  | "conflict_selection"
  | "direct_question"
  | "table_intervention"
  | "new_information"
```

#### 让五声再说一轮

用户动作：

> 你们五个看完彼此的话，再说一轮。

生成规则：

- 五声必须引用至少一个其他声音的观点。
- 不重复第一轮内容。
- 每声输出短段自然回应，不再套第一轮六项立论结构。

#### 让某一声继续说

用户动作：

> 我想听「搞钱的我」继续说。

操作台形式：

```text
让某声继续：选择声音 → 让它说
```

生成规则：

- 该声音基于本次议题、所有已有发言、用户动作继续展开。
- 它可以承认其他声音指出的代价，但不能失去自己的价值立场。

#### 选择两声对峙

用户动作：

> 让 A 问 B。

操作台形式：

```text
两声对峙：A → B
```

含义：A 看过 B 的立论和发言后，基于自己的立场向 B 发难；B 回答。

```ts
type DuelTurn = {
  from_voice_id: VoiceId
  to_voice_id: VoiceId
  question: string
  response: string
  unresolved_point: string
}
```

对峙规则：

- A 的问题必须指出 B 的盲点或代价。
- B 的回应必须保留自己的保护意图，同时承认一个代价。
- 不攻击、不讽刺、不把对方说成错。
- 对峙后书记员记录这是一组显著冲突。

#### 用户问某一声

用户动作：

> 我问「被牵挂的我」一句……

操作台形式：

```text
问某一声：选择声音 → 输入问题 → 发送
```

生成规则：

- 被点名声音回应用户。
- 回应必须使用全桌上下文，而不是只看用户这一句。
- 如果用户是在纠正它，回应先承认“这句我听见了”。

#### 用户问全桌

用户动作：

> 我问大家一句……

操作台形式：

```text
问全桌：输入发言 → 发送
```

生成规则：

- 这是用户正式参与圆桌。
- 书记员先把用户发言记录为事实、感受、偏好、反驳或新约束。
- 五声依次回应这句话。

### 6.7 Scribe Trace

书记员不输出声浪，不计算谁最大声，也不对每个声音打显著性分。它记录的是用户在圆桌中的动作痕迹，以及这些动作可能透露出的偏好假设。

```ts
type ScribeTrace = {
  requested_rounds: TraceItem[]
  requested_voices: TraceItem[]
  direct_questions: TraceItem[]
  table_interventions: TraceItem[]
  selected_conflicts: ConflictTrace[]
  new_information: TraceItem[]
  scribe_summaries: TraceItem[]
}

type TraceItem = {
  source: "user_action" | "user_text" | "scribe_inferred"
  target_voice_id?: VoiceId
  target_turn_id?: string
  text: string
  evidence_status: EvidenceStatus
}
```

书记员从这些动作中形成偏好刻画草稿，但仍然不使用精确分数。

```ts
type PreferenceProfile = {
  hypotheses: PreferenceHypothesis[]
  validated_leanings: ValidatedLeaning[]
  resisted_positions: ResistedPosition[]
  requested_perspectives: RequestedPerspective[]
  conflict_judgments: ConflictJudgment[]
  accepted_tradeoffs: string[]
  refused_tradeoffs: string[]
  unresolved_tensions: string[]
  user_self_statements: string[]
}
```

这里记录的是：

- 用户更靠近哪些声音背后的价值。
- 用户反复质询或抗拒哪些观点。
- 用户主动要求哪些声音继续说。
- 用户选择了哪些对峙关系。
- 用户已经愿意承认哪些代价。
- 用户拒绝承认哪些代价。
- 哪些东西对用户似乎不可牺牲。
- 用户亲口说过的自我判断。

`hypotheses` 是书记员的推测，用于后续问询验证；未验证前不能写进清明句。

### 6.8 Phase B: 书记员问询

自由圆桌后，书记员进入第二段工作：

- 观察用户更常靠近哪些价值。
- 找出用户反复抗拒的观点。
- 找出最针锋相对的两个声音。
- 带着推测向用户提出少量问题。
- 验证用户在五声之间的真实倾向。

书记员的问题不是追问背景，而是验证圆桌中已经出现的偏好。问询以选择题为主，仍保留“我自己说”。

自由圆桌结束后，书记员自动进入问询。问询必须完成，才能进入清明落定。

问题数量不做硬编码。停止标准不是“问满几题”，而是书记员已经能给出足够清楚的偏好刻画：

- 用户更靠近哪些声音背后的价值。
- 用户在哪两类价值之间仍然摇摆。
- 用户愿意承认哪些代价。
- 用户拒绝承认哪些代价。
- 用户此刻是有倾向、要验证、要暂缓，还是要先立边界。

例：

> 搞钱的我和被牵挂的我刚才冲突很明显。你更接近“先守住现实退路”，还是“先回应家人的担心”？

书记员问询的类型：

#### 价值偏好题

验证用户更靠近哪种价值。

```text
刚才你多次停在“退路”和“关系”之间。
如果只能先照顾一个，你此刻更想先照顾哪边？
```

#### 代价承认题

验证用户是否愿意承认某个选择代价。

```text
如果你先保护自主，你愿意承认妈妈可能继续担心一段时间吗？
```

#### 被忽略声音题

检查用户是否过快排除了某个声音。

```text
你刚才很少回应「躺平的我」。它说的“先恢复再判断”，是完全不准，还是你暂时不想听？
```

#### 对峙裁决题

围绕最显著冲突，让用户裁决更接近哪里。

```text
「搞钱的我」说先算退路，「出走的我」说先救回呼吸感。
哪一句更像你现在不敢承认的真话？
```

#### 姿态题

判断是否已经适合进入清明落定。

```text
你现在更像是已经有倾向，还是只是终于知道自己为什么不能急着决定？
```

### 6.9 Roundtable Stop Point

圆桌不需要强制固定轮数。自由圆桌阶段由用户决定何时结束，随后必须经过书记员问询。书记员可以在这些条件出现时提示用户结束自由圆桌：

- 五个声音都至少表达过一轮。
- 用户至少完成一次真实操作，例如继续某声、问某声、问全桌或选择对峙。
- 至少有一个主要冲突被点亮。

提示文案可以是：

> 书记员觉得，这场圆桌已经浮出一个清楚的分歧。可以继续聊，也可以让我问几个确认问题。

主动作：

```text
继续圆桌
进入书记员问询
```

## 7. Stage Three: 清明落定

清明句由书记员整理，不再强调 NowMe 作为独立角色。

输入材料：

- 本次议题。
- 五声圆桌结构化发言。
- 用户在圆桌中的动作痕迹。
- 书记员问题的回答。
- 用户对清明句的最终改写。

输出：

```ts
type ClarityResult = {
  clarity_sentence: string
  preference_readout: string
  tradeoff_acknowledgement: string
  settlement_posture: SettlementPosture
  commitment24h: string
  user_revision?: string
}
```

清明落定的交付物不是“模型总结”，而是一份用户可以带走的结晶：

- 一句清明句。
- 一段五声偏好读数。
- 一个代价承认。
- 一个此刻落点。
- 一个 24h 承诺。

### `clarity_sentence`

一句用户愿意承认的真实判断。

形式可以接近：

> 我现在看清楚的是：我不是在纠结 A，而是在 B 和 C 之间选择先保护什么。

清明句可以使用“不是 X，而是 Y”的结构，但不强制。更重要的是：它必须从用户在圆桌中的选择和问询回答里长出来。

用户可以改写清明句。改写不会反向更新书记员的数据判断，但书记员必须把“用户如何改写”如实记录为 `user_revision`。

### `preference_readout`

书记员用自然语言说明：圆桌过程中，用户更靠近哪些价值，仍在哪些价值之间摇摆。

例：

> 你不是单纯更相信搞钱的我，而是更需要它提供退路；同时你没有否认被牵挂的我，只是不想让关系压力替你做决定。

它不使用分数，不排名，不说“声浪最大”。它只说明用户在圆桌中显露出来的倾向和证据。

### `tradeoff_acknowledgement`

承认选择的代价。

例：

> 如果我先保护自主，我要承认妈妈可能继续担心。

### `settlement_posture`

此刻落点。它不是心理标签，而是清明句之后用户最适合站在哪种位置。

```ts
type SettlementPosture =
  | "leaning"
  | "not_ready"
  | "testing"
  | "boundary"
  | "grieving"
```

含义：

- `leaning`：已经有倾向，但还需要承认代价。
- `not_ready`：还不能决定，但已经知道卡在哪里。
- `testing`：适合用一个小实验验证。
- `boundary`：先处理边界，再处理大决定。
- `grieving`：先承认失去或难过，不急着行动。

### `commitment24h`

保留 24h 承诺。它是清明句落地的最小动作，但不应该被写成宏大计划。

它可以是：

- 验证一个事实。
- 和某个人说一句边界。
- 列一张数字表。
- 写下真实倾向。
- 完成一个 10 分钟的小实验。
- 做一个恢复性动作。

约束：

- 24 小时内能做。
- 动词开头。
- 不要求改变人生。
- 不替用户做重大决定。
- 若 `settlement_posture` 是 `not_ready`，承诺可以是“暂不决定，但做一个澄清动作”。

## 8. Technical Reset

v0.7 可以作为技术重构版本，不需要兼容旧会谈链路。

原则：

- 新 IndexedDB 库名，例如 `ParallelMeV7`。
- 不迁移旧记录。
- 不保留旧会谈流程作为用户路径。
- API 可以重写，不必围绕 `/api/focus`、`/api/voices`、`/api/clarify`、`/api/nowme` 做兼容。
- 页面可以重构为新的三段动线：本次议题、五声圆桌、清明落定。

type V7Meeting = {

## 10. Acceptance

v0.7 成功时，用户应该能说出：

- “我只写了一段原始想法，系统就帮我把议题摊清楚了。”
- “我没有被迫一路填表，只是做了几次高密度选择。”
